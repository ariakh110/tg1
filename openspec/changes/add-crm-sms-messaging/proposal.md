# Change: CRM SMS messaging (Kavenegar) — send SMS to customers + purchase-step notifications

## Why
The CRM stores customers (with a unique phone) but there is **no way to actually message them**. The only notification code today is a stub in `sales/services.py` (`SMS_PROVIDER_ENABLED`) that records a `StoreOrderNotification` but never calls any provider. The team needs to (1) send SMS to existing CRM customers — one-off and to a filtered segment — and (2) send purchase-step SMS to customers during direct sales. The first provider is the **Kavenegar** panel (API doc bundled at `openspec/sms-kavenegar-api-doc/api-doc.md`).

## What Changes
- **New `messaging` Django app (admin-only), channel-extensible.** Built SMS-first; the `channel` field + a `providers/` package leave room for Telegram/WhatsApp later without reshaping the data model.
  - `MessagingSettings` (singleton): master `sms_enabled` switch, `provider` (default `kavenegar`), Kavenegar `api_key` (secret, **write-only** in the API), default `sender` line, optional `verify/lookup` template names (default + purchase-step), and a `daily_send_cap` safety limit. Mirrors `SiteSettings` / `SeoAssistantSettings` singletons; the key is never returned by GET.
  - `OutboundMessage` (audit log): `channel`, `provider`, optional `customer`, `recipient`, `purpose` (manual/bulk/order_status/otp), `template`, `body`, `status` (queued/sent/delivered/failed/skipped), `provider_message_id`, `cost`, `error`, `created_by`, timestamps.
- **Kavenegar provider (`providers/kavenegar.py`) using raw `urllib`** (no new pip dependency, consistent with `seo_assistant/ai.py`). Supports `sms/send` (free-text, for CRM blasts), `verify/lookup` (template-based, high-priority/never-filtered — for transactional purchase-step messages), and `sms/status`. Iranian phone normalization (`+98`/`0098` → `09…`).
- **Channel-agnostic service (`service.py`).** `send_sms`, `send_to_customer`, `send_bulk`, and `notify_purchase_step`. **Dry-run when disabled/unconfigured:** if `sms_enabled` is off or no key is set, the attempt is logged with status `skipped` (no error) so the whole flow is testable before credentials exist. Real sends update the log with the provider message id, cost, and status. Sends to a customer also append a `CustomerActivity(kind=message)` to that customer's timeline.
- **APIs (admin-only, mounted at `/api/messaging/`).** `GET/PATCH settings/`; `POST send/` (single, by `customer_id` or `recipient`); `POST send-bulk/` (segment by ids or stage/source filter); `POST notify-step/` (purchase-step); `GET messages/` (filterable log). New `messaging` admin section, available to the MARKETER role.
- **Inbound Kavenegar webhooks (public, secret-guarded).** `kavenegar/status/<secret>/` (delivery-status callback → updates the matching `OutboundMessage` from the Kavenegar status code) and `kavenegar/incoming/<secret>/` (receive callback → appends a `CustomerActivity(message)` when the sender matches a customer). The secret is auto-generated into `MessagingSettings.webhook_secret` and returned (read-only) so the admin can paste the full callback URLs into the Kavenegar panel.

## Impact
- Affected specs: `messaging` (new capability)
- Backend (tg1): new app `messaging` (models, providers/, service, serializers, views, urls, admin, apps, migration `0001`, tests); register in `INSTALLED_APPS`, root urls at `/api/messaging/`, and add `messaging` to `accounts/admin_sections.py` (`ADMIN_SECTIONS` + MARKETER). No changes to existing tables; the `sales` stub may later call this service (out of scope here).
- Frontend (kavehmetal): out of scope for this change; admin can drive it via the API. A CRM "ارسال پیامک" button + bulk action + a settings tab are a follow-up.
- **Disabled by default.** No SMS is sent until an admin enables `sms_enabled` and pastes a Kavenegar key in the panel; until then everything is dry-run. WhatsApp (needs a separate gateway — Kavenegar has none) and Telegram (needs per-customer `chat_id` opt-in) are deferred to later phases.
