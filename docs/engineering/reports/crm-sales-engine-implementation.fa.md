# گزارش پیاده‌سازی موتور فروش CRM

تاریخ: ۲۰۲۶-۱۱-۰۷  
وضعیت: پیاده‌سازی محلیِ برش تأییدشده کامل است؛ migration روی پایگاه داده اجرا نشده است.

## دامنه و تصمیم‌های تثبیت‌شده

- اپراتور فعلی یک نفر است؛ task فقط وقتی خودکار به مالک وصل می‌شود که یک اپراتور فعالِ یکتا پیدا شود. در غیر این صورت بدون مالک و در صف می‌ماند.
- task و یادآوری داخلی خودکارند. ارسال SMS یا بله به مشتری همیشه با اقدام دستی اپراتور انجام می‌شود.
- برای task تازه موعد ساختگی تعیین نمی‌شود. مورد بی‌موعد در صف «نیازمند اقدام» یا «بدون موعد» می‌ماند.
- فرصت از مدل فعلی `Customer` به‌عنوان هویت سرنخ استفاده می‌کند؛ مدل مستقل `CrmLead` در این برش ساخته نشده است.
- سفارش/استعلام و مراحل آن‌ها همچنان از مدل و جریان اصلی سایت می‌آیند؛ CRM نسخهٔ تراکنشی موازی ایجاد نمی‌کند.

## آنچه پیاده شد

- مدل‌های `CrmTask`، `CrmFollowUp`، `CrmAutomationRun` و `CrmContactChannel` اضافه شدند. `CustomerActivity` هم به فرصت وصل شد و جهت، نتیجه و شناسهٔ پیام بیرونی گرفت.
- migration افزایشی `customers/migrations/0009_crm_sales_engine.py` ساخته شد. پیگیری‌های بازِ قدیمی از activity به `CrmFollowUp` کپی می‌شوند و کلید یکتای مبتنی بر activity دارند تا اجرای دوباره کپی تکراری نسازد.
- فهرست مشتریان به صفحه‌بندی سمت سرور با اندازهٔ پیش‌فرض ۵۰ و سقف ۱۰۰ تغییر کرد؛ جست‌وجو و فیلتر مرحله/منبع هم سمت سرور اعمال می‌شود.
- اتوماسیون whitelist برای `customer.created` و `opportunity.stage_changed` ثبت اجرای idempotent، ساخت task داخلی و retry خطا را اضافه کرد. بستن فرصت، taskها و پیگیری‌های باز آن را لغو می‌کند.
- API صف، task، پیگیری، اجرای اتوماسیون، ثبت رضایت کانال و فرصت دستی اضافه/تکمیل شد. فعالیت قدیمی مشتری و شمارنده‌های پیگیری با دادهٔ جدید سازگار می‌مانند.
- پنل مستقل صف فروش با گروه‌های عقب‌افتاده، امروز، سرنخ‌های تازه، فرصت‌های نیازمند اقدام، بدون موعد و آینده ساخته شد؛ پیگیری‌های قدیمی هم بر اساس موعد خود در گروه زمانی درست می‌آیند. صف ثبت نتیجه، تعویق با موعد تازه، ساخت task برای فرصت، تلاش دوبارهٔ اجرای ناموفق و بازکردن پرونده/فرصت دارد.
- قیف فرصت‌ها فرصت دستی می‌سازد و تاریخچهٔ مرحله را حفظ می‌کند؛ فرصت‌های متصل به سفارش یا استعلام سایت در UI با جریان منبع خود تغییر می‌کنند.
- ارسال تکی و کمپین به `confirmed: true` نیاز دارند. CRM-linked فقط با رضایت ثبت‌شده برای همان کانال مجاز است؛ پیش‌نمایش کمپین مخاطبان حذف‌شده به‌علت رضایت را نشان می‌دهد و hash مخاطب هنگام ارسال دوباره بررسی می‌شود. هیچ provider فراخوانی نشد.

## APIهای این برش

- `GET /crm/work-queue/`
- `GET/POST /crm/tasks/`، به‌همراه `complete` و `snooze`
- `GET/POST /crm/follow-ups/`، به‌همراه `complete`، `snooze` و `cancel`
- `GET /crm/automation-runs/` و `POST /crm/automation-runs/{id}/retry/`
- `PUT /crm/customers/{id}/contact-channels/`
- ایجاد فرصت دستی از `POST /crm/opportunities/`

همهٔ endpointهای جدید زیر permissionهای پنل CRM باقی می‌مانند.

## بررسی و محدودیت‌ها

- `python -m py_compile` برای ماژول‌های تغییرکردهٔ Django: موفق.
- `manage.py check`: موفق، بدون خطای system check.
- `makemigrations --check --dry-run customers`: «No changes detected». بررسی تاریخچه به PostgreSQL محلی وصل نشد چون `localhost:5432` در دسترس نبود.
- ESLint روی فایل‌های CRM (صف، مشتری، قیف، کمپین، پیام‌رسان و APIهای فرانت‌اند): موفق.
- اجرای ESLint روی `AdminDashboardPage.js` نیز پنج خطای موجود در بخش‌های دیگر همان فایل نشان داد: ساخت کامپوننت آیکون هنگام render و چهار بار فراخوانی loader از effect. بررسی کد نشان می‌دهد این خطوط خارج از تغییر CRM هستند.
- `git diff --check`: بدون خطای whitespace؛ Git فقط دربارهٔ تبدیل پایان‌خط دو فایل فرانت‌اند هشدار داد.
- تست، build، مرورگر و پایگاه دادهٔ واقعی اجرا نشدند. migration اعمال، provider فراخوانی، پیام ارسال، deploy یا انتشار انجام نشد.
- بازبینی spec و کیفیت در همین نشست و توسط همان مجری انجام می‌شود؛ بازبین مستقل در دسترس/مجاز نبود.

## دامنهٔ باقی‌مانده در OpenSpec

این برش صف فروش است، نه تکمیل همهٔ برنامهٔ CRM. مدل و inbox مستقل Lead، تنظیم stageها، metadata پیوست activity، feature flag/rollback، sequence و template پیام، custom field، تختهٔ drag-and-drop، فیلترها و گزارش‌های کامل، عملیات نوشتنی Bale و گردش Excel پیاده نشدند. taskهای متناظر در `openspec/changes/add-site-native-crm-workspace/tasks.md` باز می‌مانند.

قبل از استفاده روی محیط عملیاتی، migration باید در محیط دارای PostgreSQL بررسی و اعمال شود و رفتار با دادهٔ همان محیط بازبینی گردد. وضعیت محلی به معنی deploy یا ارسال موفق پیام نیست.
